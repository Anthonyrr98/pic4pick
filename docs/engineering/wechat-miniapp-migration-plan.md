# Pic4Pick 微信小程序完整迁移计划

评估日期：2026-10-13。状态：代码静态审查后的初步计划，尚未创建小程序工程或完成微信真机验证。

## 目标与范围

使用 Taro + React + TypeScript 增加微信小程序，网页与小程序共用内容、后台及平台无关业务逻辑，持续同步迭代。

本计划中的“完整迁移”包含当前实际接入的公开图库和管理员功能，以及地图探索、原图保存、两种主题和空间场景。以功能等价和手机交互适配验收，不承诺浏览器界面、桌面悬停、快捷键或地图底图逐像素一致。浏览器专有配置在小程序中保留其网页配置用途，不能自动转换成小程序能力。

网页继续沿用 React + Vite。本次包括提取共享逻辑、必要的数据接口改造和网页回归；将整个网页及网页后台也迁入 Taro 是额外项目，不包含在下列估算中。

不额外引入公众用户注册、微信账号绑定、评论、付费、订阅通知等产品功能。分享作品是小程序适配项，支持按照片 ID 进入详情。

## 代码审查依据

- `src/App.jsx`：React Router、浏览器 sessionStorage 和启动动效。
- `src/pages/gallery/GalleryPage.jsx`：实际公开页面、照片详情、原图下载和空间场景入口。
- `src/pages/gallery/components/PhotoGrid.tsx`：响应式图片、列表加载、浏览器测量和鼠标倾斜效果。
- `src/pages/gallery/utils/photoFilterUtils.ts`：最新、随览、附近、远方和胶片筛选，可提取公共规则。
- `src/pages/gallery/hooks/usePhotoData.ts`：Supabase 数据读取、最多 1000 条加载、本地缓存和点赞请求。
- `src/pages/gallery/hooks/useExifAndLocation.ts`：浏览器定位、原图 EXIF 读取、第三方海拔服务。
- `src/pages/gallery/components/ExploreView.jsx`、`PhotoLocationMap.jsx`：高德 Web / MapLibre、DOM 标记和地图运动。
- `src/pages/Admin.jsx`：实际管理流程，约 5000 行，包括上传、审核、编辑、批量操作、地图选点和配置。
- `src/components/admin/ConfigPanel.jsx`：环境参数、网页地图样式、Logo 与品牌文字。
- `src/themes/themeConfig.js`：纸白画廊、暖调胶片主题及浏览器应用方式。
- `src/utils/spatialRenderer.js`、`src/hooks/useSpatialScene.js`：WebGL 着色器、浏览器 Canvas、页面尺寸和设备方向监听。
- `docs/spatial-scenes.md`：后台 SharpDepth + UniDepth 预计算、私有 OSS 深度图、签名接口和任务队列。
- `server/server-enhanced.js`：管理员鉴权、上传、点赞、深度图签名和管理 API。

仅存在但未接入当前页面的旧组件不自动计入迁移范围，例如已移除的图片压缩工具面板；工程搭建后应再次核对可达页面和实际线上功能。

## 技术组织

先在现有仓库增加 `miniapp/` 与 `packages/shared/`，避免为搭建小程序立即移动全部现有文件。共享层稳定后再按需要整理 `apps/web`、`apps/miniapp`，移动目录本身不是阶段验收目标。

- 公共层：照片类型、字段规范、分类、筛选与排序规则、时间和距离计算、品牌与主题参数、API 契约。
- 平台适配层：请求、缓存、图片加载、文件上传与保存、导航、定位、页面生命周期、地图和 Canvas。
- 界面层：网页保留现有实现；小程序采用 Taro 组件和手机布局。Hooks 逐个判断依赖，不能因为使用 React 就直接共享。
- 后端：复用 Express、数据库、OSS 和 GPU worker；为小程序补齐稳定的公开读接口及必要的元数据处理。
- 公开读接口：只返回已审核且未隐藏的作品及必要字段；明确分页、随机排序、附近/远方排序语义，不在局部分页上冒充全量排序。
- 管理接口：继续由服务端验证管理员权限。小程序客户端不包含数据库高权限凭据、OSS Secret 或签名密钥。
- 两端共用同一份内容；跨设备点赞状态目前不是用户账号同步功能，不能把浏览器本地点赞记录视为自动同步。

## 最需要先验证的四个问题

### 1. 地图能否满足现有探索体验

现有实现依赖 Web 地图库、HTML 标记和定制运动。小程序原生地图必须重新实现标记、选点、城市跳转和列表联动。数据库 EXIF 坐标、浏览器定位和小程序地图坐标需明确各自坐标系，避免重复转换或位置偏移。

原生地图不能默认复刻当前网页的底图样式和每个运动效果。阶段 0 用实际国内、海外作品及管理员选点验证，形成对应功能清单。若需要另建自绘地图以满足特定视觉要求，须重新估算。

### 2. 原图上传与 EXIF 能否保真

网页支持最大 100 MB 文件，超过阈值可能先压缩；小程序的相册、临时文件和上传接口不是浏览器 File/Blob。测试 JPG、PNG、WebP、大图、旋转方向和拍摄参数，在 iOS/Android 分别记录结果。

选取“original”只代表选择策略，不应直接认定每个来源都保留原始文件字节和全部 EXIF。可以在获得文件后用服务端读取原始 EXIF，再生成预览；缺失信息允许手动填写。验证结果决定是否需要额外文件选择入口或上传方式。

### 3. 空间场景的真机性能

模型、任务队列和深度图生成留在现有后台，无需把推理模型迁入小程序。可复用 shader 和输入数学逻辑，但浏览器 Canvas/DOM、`ResizeObserver`、图片对象、帧调度和姿态监听必须适配。

阶段 0 用多种宽高比作品验证纹理上传、深度灰度读取、拖动和倾斜。覆盖横竖屏、签名过期、内存紧张、频繁切换、退后台和渲染失败。完整迁移需在目标设备上支持该功能；故障降级仅用于异常恢复，不能用它代替功能交付。

### 4. 国内网络和账号能力

在微信真机验证现有 API、数据库访问链路、OSS/CDN、深度签名和第三方地理服务，记录冷启动和弱网行为。优先让小程序通过受控后端访问公共数据与第三方服务，减少直接依赖浏览器 SDK。

核对小程序主体、发布类目、定位使用条件、HTTPS 与各类合法域名配置，以及相关备案/审核要求。规则按实施时的平台后台和官方文档确认，本计划不假定账号与域名条件已经满足。

## 里程碑与实施顺序

1. M0：2–4 人日形成真机技术验证报告，收紧完整迁移估算。若发现能力限制，先明确其影响和对应实现，不在后期才处理。
2. M1：阶段 1–4，公开图库体验版，两端共用数据和核心规则。
3. M2：完成地图、空间效果及管理端模块；共享地图基础能力完成后进入管理员选点与上传流程。模块自测合格后进入整体验收。
4. M3：两端联调与真机验收、发布候选版、提交审核准备。

## 完整迁移验收清单

- 两端照片 ID、公开字段、审核/隐藏状态、品牌内容一致。
- 最新、随览、附近、远方、胶片规则一致；长列表加载不重复、不遗漏，不因缓存或分页破坏排序。
- 详情、拍摄日期、器材、EXIF/地点、海拔、点赞、高清预览和原图保存正常。
- 分享可进入指定公开作品；删除、隐藏或未审核作品有正确反馈。
- 地点探索和管理员选点准确，国内/海外坐标和缺失地理信息有明确处理。
- 空间场景在目标设备可用，签名过期可恢复，页面切换和后台状态正确释放资源。
- 管理员可完成上传、审核、拒绝、重新提交、编辑、隐藏、单个/批量删除、统计、品牌和配置操作。
- 未登录或无权限的客户端不能执行管理操作，公开接口不泄露非公开作品或高权限密钥。
- 目标 iOS/Android 真机通过；弱网、拒绝授权、服务冷启动、大图和操作中断可恢复。
- 网页现有图库、地图、空间场景、主题、上传、审核、编辑和删除回归通过。
